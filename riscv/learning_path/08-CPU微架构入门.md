# 08 CPU 微架构入门

**前置阅读**：[[07-标准扩展学习|← 07 标准扩展学习]]

## 你要学什么

前面你学的都是 **ISA（Instruction Set Architecture，指令集架构）**：CPU 必须支持哪些指令，每条指令做什么。

但同样的指令集，为什么有的芯片快，有的芯片慢？这就是 **微架构（Microarchitecture）** 的差异。

### 为什么要学这个？

上一章你知道了扩展决定芯片能做什么，但看芯片规格时还会遇到"5级流水线"、"乱序执行"、"64KB缓存"这些词。

**这一章解决的问题：**
- ISA 和微架构有什么区别？
- 流水线、乱序执行、缓存是什么？
- 为什么同样的程序在不同芯片上快慢差10倍？

学完后，你就能理解性能差异的来源，选芯片时不只看ISA，还要看微架构。下一章会教实际开发——怎么编译运行程序。

---

## 从生活例子开始

想象一家餐厅做汉堡：

### 场景：制作100个汉堡

**菜谱（ISA）规定：**
1. 煎肉饼
2. 烤面包
3. 加生菜
4. 加酱料
5. 组装

**结果必须一样：汉堡要好吃，步骤不能错。**

### 方法1：一个人做（简单微架构）

一个厨师按顺序做：
1. 做完第1个汉堡的所有步骤
2. 开始做第2个汉堡
3. ...

**耗时**：100个汉堡 × 5分钟 = 500分钟

### 方法2：流水线（Pipeline）

5个厨师分工：
- 厨师A：专门煎肉饼
- 厨师B：专门烤面包
- 厨师C：专门加生菜
- 厨师D：专门加酱料
- 厨师E：专门组装

**流程：**
```
时间  A     B     C     D     E
1分   #1    -     -     -     -
2分   #2    #1    -     -     -
3分   #3    #2    #1    -     -
4分   #4    #3    #2    #1    -
5分   #5    #4    #3    #2    #1   ← 第1个汉堡完成
6分   #6    #5    #4    #3    #2   ← 第2个汉堡完成
...
```

**耗时**：5分钟启动 + 100分钟 = 105分钟

**快了近5倍！**

## ISA vs 微架构

### ISA（指令集架构）

**定义：CPU 对软件的承诺。**

```asm
add x5, x6, x7    # ISA 保证：x5 = x6 + x7
```

- 所有 RISC-V CPU 必须按照规范执行
- 程序编译一次，在所有 RISC-V 芯片上运行
- **ISA 不关心 CPU 内部怎么实现**

### 微架构（Microarchitecture）

**定义：CPU 内部的实现方式。**

同样的 `add` 指令，不同微架构：

| 微架构特征 | 简单实现 | 高性能实现 |
|-----------|----------|-----------|
| 流水线级数 | 2-3级 | 10-15级 |
| 每周期执行指令数 | 1条 | 4-6条 |
| 乱序执行 | 无 | 有 |
| 分支预测 | 无 | 复杂预测器 |
| 缓存 | 无或小 | L1/L2/L3多级 |
| 性能 | 慢 | 快 |
| 功耗 | 低 | 高 |
| 成本 | 便宜 | 贵 |

**类比：**
- **ISA = 菜谱**：规定汉堡怎么做
- **微架构 = 厨房组织方式**：一个人做还是流水线做

## 流水线（Pipeline）

### 最简单的CPU：单周期执行

每条指令分5步完成：

```
指令1: [取指][解码][执行][访存][写回]
指令2:                              [取指][解码][执行][访存][写回]
```

**问题**：一次只能处理一条指令，其他部件闲着。

### 流水线CPU

5个步骤同时进行，处理不同指令：

```
周期  取指  解码  执行  访存  写回
1     指令1
2     指令2  指令1
3     指令3  指令2  指令1
4     指令4  指令3  指令2  指令1
5     指令5  指令4  指令3  指令2  指令1
```

**好处**：每个周期完成一条指令（吞吐量×5）

**代价**：
- 硬件更复杂
- 遇到跳转需要清空流水线（Pipeline Stall）

### 流水线冒险（Hazard）

#### 1. 数据冒险（Data Hazard）

```asm
add x5, x6, x7    # 指令1：写 x5
sub x8, x5, x9    # 指令2：需要读 x5（但还没写完！）
```

**解决方法：**
- **停顿（Stall）**：指令2等指令1完成
- **前递（Forwarding）**：直接把结果传给指令2，不等写回

#### 2. 控制冒险（Control Hazard）

```asm
beq x5, x6, target    # 如果相等，跳转
add x7, x8, x9        # 后续指令已经进入流水线
```

**问题**：还不知道是否跳转，后续指令怎么办？

**解决方法：**
- **分支预测（Branch Prediction）**：猜测跳不跳，猜错了重新来

## 乱序执行（Out-of-Order Execution）

### 问题：顺序执行浪费时间

```asm
lw   x5, 0(x10)     # 指令1：从内存读（慢，需要100个周期）
add  x6, x5, x7     # 指令2：依赖 x5，必须等
mul  x8, x9, x10    # 指令3：不依赖 x5，可以先做！
```

**顺序执行**：指令3要等指令1和2完成。

**乱序执行**：CPU 发现指令3不依赖，提前执行。

```
时间  指令1(lw)   指令3(mul)  指令2(add)
1-100 内存读取中    执行        等待
101                完成        执行
```

**好处**：充分利用 CPU 资源，不浪费等待时间。

**代价**：硬件复杂得多。

---

## 缓存（Cache）

### 问题：内存太慢

- **寄存器**：1个周期
- **内存**：100-200个周期

如果每次都访问内存，CPU 大部分时间在等待。

### 解决：缓存

在 CPU 和内存之间加几层快速存储：

```
CPU → L1 缓存（1-3周期，32KB）
    → L2 缓存（10-20周期，256KB）
    → L3 缓存（30-40周期，8MB）
    → 内存（100+周期，几GB）
```

**原理：**
- 程序有**局部性**：最近用过的数据，很可能再次使用
- 把常用数据放在缓存里
- 命中率通常 > 90%

**例子：**
```asm
lw   x5, 0(x10)     # 第一次：从内存读（慢）
lw   x6, 0(x10)     # 第二次：从缓存读（快！）
```

## 实际芯片对比

### 1. SiFive E20（嵌入式）

- **ISA**：RV32IMC
- **微架构**：
  - 2级流水线
  - 顺序执行
  - 无缓存
  - 50 MHz
- **性能**：0.5 DMIPS/MHz
- **应用**：IoT传感器、低功耗设备

### 2. 晶心 N25（实时控制）

- **ISA**：RV32IMAC
- **微架构**：
  - 5级流水线
  - 顺序执行 + 分支预测
  - 可配置缓存（8-64KB）
  - 可达 1 GHz
- **性能**：3.8 CoreMark/MHz
- **应用**：汽车电子、工业控制

### 3. 阿里平头哥玄铁910（高性能）

- **ISA**：RV64GCV
- **微架构**：
  - 12级流水线
  - 乱序执行，3发射
  - 3级缓存（L1 64KB, L2 512KB, L3共享）
  - 2.5 GHz
- **性能**：7.5 CoreMark/MHz
- **应用**：服务器、AI推理、边缘计算

### 性能对比

同样执行 `add x5, x6, x7`：

| 芯片 | 周期数 | 频率 | 实际耗时 |
|------|--------|------|----------|
| E20  | 1周期 | 50 MHz | 20 ns |
| N25  | 1周期 | 1 GHz | 1 ns |
| 玄铁910 | 1周期（流水线吞吐） | 2.5 GHz | 0.4 ns |

**同样的指令，速度差50倍！**

## 为什么微架构重要

### 软件视角

```c
// 同样的C代码
int sum = 0;
for (int i = 0; i < 1000; i++) {
    sum += array[i];
}
```

**编译成同样的 RISC-V 指令，但：**
- 在 E20 上：需要 50,000 个周期
- 在玄铁910上：可能只需要 5,000 个周期（因为乱序执行、缓存、向量化）

### 硬件选择

**选芯片时要问：**
1. **功耗预算**：电池供电 → 简单微架构
2. **性能要求**：实时响应 → 中等性能
3. **计算密集**：AI/服务器 → 高性能微架构
4. **成本**：大规模量产 → 尽可能简单
