## 带宽

**带宽**（Bandwidth）是指单位时间内可以传输的数据量，通常用 **GB/s**（每秒多少 GB）或 **MB/s** 表示。

### 核心概念

**带宽 = 通道数 × 每通道宽度 × 传输速率**

### K3 的 LPDDR5 带宽计算

```
K3 的 LPDDR5：
- 2 个通道（双通道）
- 每通道 32 位 = 4 字节
- 传输速率 6400 MT/s

理论带宽 = 2 × 4 字节 × 6400 = 51.2 GB/s
```

### 类比理解

```
带宽 = 高速公路的通行能力
- 通道数 = 车道数（2 条）
- 通道宽度 = 每条车道的宽度（4 字节）
- 传输速率 = 车辆通过速度（6400 次/秒）

带宽越大 = 同时能运输更多货物
```

### 为什么带宽很重要？

**AI 推理场景**：
- A100 核心需要从内存读取模型权重（几百 MB 到几 GB）
- 如果带宽不够，A100 会空转等待数据
- **算力再高，数据送不到也没用**

**瓶颈判断**：
- 算力高、带宽低 → CPU 等数据（带宽瓶颈）
- 算力低、带宽高 → 数据等 CPU（算力瓶颈）

### 实际带宽 vs 理论带宽

- **理论带宽**：51.2 GB/s（计算上限）
- **实际带宽**：通常只有理论值的 70-90%（因为有协议开销、刷新周期等）

**相关概念**：LPDDR5、内存带宽、双通道

## 内存与存储

**内存**（Memory）和**存储**（Storage）是两个容易混淆但本质不同的概念。

### 核心区别

| 特性 | 内存（RAM） | 存储（Storage） |
|---|---|---|
| 作用 | 临时存放正在运行的程序和数据 | 永久保存文件和数据 |
| 速度 | 快 | 慢 |
| 断电后 | 数据丢失 | 数据不丢失 |
| 容量 | 较小（K3 最高 32 GB） | 大（K3 最高 2 TB） |

### 类比理解

```
内存 = 办公桌
- 正在处理的文件摊在桌上
- 拿取方便、速度快
- 下班清空、面积有限

存储 = 文件柜
- 所有文件归档保存
- 翻找较慢、容量大
- 永久保留
```

### K3 的内存与存储

| 类型 | 技术 | 作用 |
|---|---|---|
| 内存 | LPDDR5 | 运行操作系统、应用、AI 模型 |
| 存储 | eMMC/SD | 保存文件系统、视频、照片 |

### 工作流程

1. 程序和文件存在 eMMC（存储）
2. 运行时加载到 LPDDR5（内存）
3. CPU 从内存读取数据处理
4. 处理结果写回 eMMC 永久保存

### 为什么需要两者？

- **只有内存**：断电就丢失所有东西
- **只有存储**：速度太慢，程序跑不起来

**相关概念**：LPDDR5、eMMC、RAM、ROM

## 虚拟机

**虚拟机**（Virtual Machine，VM）是用软件模拟出来的完整计算机，可以在一台物理机器上同时运行多个独立的操作系统。

### 简单理解
就像在你的 Windows 电脑上，用软件"假装"出另一台电脑，这台"假电脑"可以运行 Linux、另一个 Windows，或者其他操作系统。

### 实际应用场景
```
物理 K3 芯片
  ├─ 虚拟机 1：运行 Ubuntu（给用户 A 用）
  ├─ 虚拟机 2：运行 Debian（给用户 B 用）
  ├─ 虚拟机 3：运行 Android（给 APP 测试用）
  └─ ... 最多 8 个虚拟机同时运行
```

每个虚拟机以为自己独占整台机器，实际上它们共享同一颗 K3 芯片的资源。

### 为什么需要虚拟化？
- **隔离**：一个虚拟机崩溃不会影响其他虚拟机
- **多租户**：一台服务器可以给多个客户用，互不干扰
- **测试**：在同一台机器上测试不同操作系统
- **云计算**：云服务器就是虚拟机

### K3 的虚拟化支持
**RVH 1.0**（RISC-V Hypervisor Extension 1.0）是 RISC-V 的硬件虚拟化扩展，**GEILEN=8** 表示 K3 的 X100 核心可以同时支持 8 个虚拟机（Guest）。

硬件虚拟化扩展让 K3 可以高效运行虚拟机，不需要纯软件模拟（纯软件模拟会很慢）。

**相关概念**：RVH 1.0、Hypervisor、云计算

## RVA23

**RVA23** 是 RISC-V 应用处理器标准的 2023 版本（RISC-V Application Profile 2023）。

### 为什么需要标准？
RISC-V 是开放指令集架构，理论上每个芯片厂商都可以实现不同的扩展，导致软件兼容性问题。RVA23 定义了一套强制要求和可选扩展，确保操作系统和应用程序可以依赖这些指令集。

### RVA23 强制要求
- 基础整数指令（RV64I）
- 乘法与除法（M）
- 原子操作（A）
- 浮点运算（F、D）
- 向量扩展（V）
- 虚拟化扩展（H）
- ... 等等

### K3 与 RVA23
K3 的 X100 核心符合 RVA23 规范，意味着为 RVA23 编写的软件可以直接在 K3 上运行。

**相关概念**：RISC-V、指令集架构、向量扩展、虚拟化扩展

## RVV 1.0

**RVV 1.0**（RISC-V Vector Extension 1.0）是 RISC-V 的向量扩展，支持 **SIMD**（Single Instruction Multiple Data，单指令多数据）计算。

### 向量扩展是什么？
传统标量指令一次只能处理一个数据：
```
a[0] = b[0] + c[0]  // 一条指令
a[1] = b[1] + c[1]  // 又一条指令
a[2] = b[2] + c[2]  // 又一条指令
...
```

向量指令一次可以处理多个数据：
```
a[0..7] = b[0..7] + c[0..7]  // 一条指令完成 8 个加法
```

### VLEN=256
**VLEN**（Vector Length）是向量寄存器的宽度，单位是位（bit）。

K3 的 X100 核心 VLEN=256 位，意味着一条向量指令可以同时处理：
- 8 个 32 位整数（256 ÷ 32 = 8）
- 4 个 64 位浮点数（256 ÷ 64 = 4）

### 为什么向量扩展很重要？
- **科学计算**：矩阵运算、物理模拟
- **图像处理**：滤波、缩放、色彩转换
- **音视频编解码**：大量并行数据处理
- **AI 推理**：神经网络层的矩阵乘法

**相关概念**：SIMD、并行计算、向量寄存器

## RVH 1.0

**RVH 1.0**（RISC-V Hypervisor Extension 1.0）是 RISC-V 的虚拟化扩展，支持硬件虚拟化。

### 虚拟化扩展是什么？
没有硬件虚拟化扩展时，虚拟机管理器（Hypervisor）需要用纯软件模拟每一条指令，效率极低。

有了 RVH 1.0，CPU 可以直接支持虚拟机的特权指令，虚拟机内的代码可以直接在 CPU 上运行，性能接近物理机。

### GEILEN=8
**GEILEN**（Guest External Interrupt Lines）是指支持的虚拟机外部中断线数量。

K3 的 X100 核心 GEILEN=8，意味着最多可以同时运行 8 个虚拟机（Guest），每个虚拟机有独立的中断处理。

### 虚拟化的两种模式
- **Host 模式**：虚拟机管理器（Hypervisor）运行的模式
- **Guest 模式**：虚拟机（VM）运行的模式

RVH 1.0 定义了 Guest 模式的指令集和特权级别，让虚拟机可以高效运行。

**相关概念**：虚拟机、Hypervisor、云计算

## IME

**IME**（Intelligent Matrix Engine，智能矩阵引擎）是 SpacemiT 为 A100 核心设计的 RISC-V 指令集扩展，专门优化矩阵运算和卷积操作。

### 为什么需要 IME？
神经网络推理的核心计算是矩阵乘法和卷积：
- **全连接层**：矩阵乘法（M × N × K）
- **卷积层**：卷积操作（大量乘加运算）

用通用核心（X100）执行这些操作，需要几十条甚至上百条指令才能完成一个矩阵块的乘法。

**IME 扩展**可以用一条指令完成复杂的矩阵操作，效率提升几十倍。

### IME 与 RVV 的区别
- **RVV 1.0**：通用向量扩展，适合各种并行计算（科学计算、图像处理、音视频编解码）
- **IME**：专门优化 AI 推理，聚焦矩阵乘法和卷积

A100 同时支持 RVV 和 IME，可以灵活选择最高效的指令。

### IME 的优势
- **高效**：一条指令完成复杂矩阵操作
- **低功耗**：专用硬件优化，能效比高
- **同构**：与 X100 共享 RISC-V 基础指令集，编程模型统一

**相关概念**：AI 加速、神经网络推理、矩阵运算、卷积

## SoC

**SoC**（System on Chip，系统级芯片）是将完整计算机系统集成在单个芯片上的设计。

### SoC vs CPU
- **CPU**：只是处理器核心，负责计算
- **SoC**：包含 CPU、内存控制器、图像处理、视频编解码、显示输出、外设、安全模块等完整系统

### 类比
- **CPU**：发动机
- **SoC**：整辆汽车（发动机 + 变速箱 + 轮胎 + 方向盘 + ...）

### K3 是一颗 SoC
K3 包含 11 个子系统，CPU 子系统只是其中之一。其他子系统包括内存、图像、视频、显示、音频、互联、安全等。

**相关概念**：CPU 子系统、芯片架构、嵌入式系统

## LPDDR5

**LPDDR5**（Low Power Double Data Rate 5）是第五代低功耗双倍数据速率内存，专为移动设备和嵌入式系统设计。

### DDR vs LPDDR
- **DDR**：桌面和服务器内存，高性能、高功耗
- **LPDDR**：移动设备内存，性能稍低、功耗更低

### 双倍数据速率（DDR）
传统内存每个时钟周期传输一次数据，DDR 内存在时钟上升沿和下降沿都传输数据，速度翻倍。

### MT/s vs MHz
- **MHz**：时钟频率，表示每秒多少百万次时钟周期
- **MT/s**：传输速率，表示每秒多少百万次数据传输

LPDDR5 每个时钟周期传输多次数据，所以用 MT/s 更准确。

### K3 的 LPDDR5
- 双通道（2 个独立的内存控制器）
- 每通道 32 位宽
- 最高速率 6400 MT/s
- 理论带宽 51.2 GB/s

**相关概念**：内存带宽、双通道、DDR

## ISP

**ISP**（Image Signal Processor，图像信号处理器）是专门处理摄像头原始数据的硬件模块。

### 为什么需要 ISP？
摄像头传感器输出的 RAW 格式图像质量很差：
- 有噪点
- 颜色不准
- 曝光不对
- 白平衡不对

ISP 把 RAW 图像处理成可用的图像（YUV 格式）。

### ISP 的主要功能
- **去噪**（Noise Reduction）：降低图像噪点
- **白平衡**（White Balance）：校正颜色温度
- **曝光补偿**（Exposure Compensation）：调整亮度
- **颜色校正**（Color Correction）：让颜色更准确
- **锐化**（Sharpening）：增强边缘细节

### RAW vs YUV
- **RAW**：摄像头传感器直接输出的原始数据，每个像素只记录一个颜色分量（红/绿/蓝）
- **YUV**：处理后的图像格式，Y 表示亮度，U 和 V 表示色度

### K3 的 ISP
K3 有独立的 ISP 子系统，可以处理多个摄像头的 RAW 图像，输出高质量的 YUV 图像给后续处理（编码、显示、AI 推理）。

**相关概念**：摄像头、RAW 格式、YUV 格式、图像处理

## VPU

**VPU**（Video Processing Unit，视频处理单元）是专门处理视频编解码的硬件加速器。

### 为什么需要 VPU？
原始视频文件巨大：
- 4K 30fps YUV420 视频每秒约 373 MB
- 1 分钟 22 GB
- 1 小时 1.3 TB

**视频编码**可以把视频压缩到原来的 1/30 甚至 1/100，大幅节省存储空间和传输带宽。

### 编码 vs 解码
- **编码**（Encoding）：把原始视频压缩成压缩格式（H.264、H.265、AV1）
- **解码**（Decoding）：把压缩视频还原成原始视频

### 软件编码 vs 硬件加速
- **软件编码**：用 CPU 计算，速度慢、功耗高、无法实时
- **硬件加速**：用 VPU 专用硬件，速度快、功耗低、可以实时

### K3 的 VPU
- **编码能力**：4K@90fps H.264/H.265 编码
- **解码能力**：4K@180fps H.264/H.265 解码
- **同编同解**：可以同时进行 4K@60fps 编码 + 解码
- **支持格式**：H.264、H.265、AV1、VP8、VP9、MPEG4、MPEG2、H.263

**相关概念**：视频编码、H.264、H.265、AV1、硬件加速

## 簇

**簇**（Cluster）是指一组共享 L2 缓存的 CPU 核心。

### 为什么需要簇？

CPU 核心需要互相通信和共享数据。把核心分成簇，让同一个簇内的核心共享 L2 缓存，可以：
- **加速数据共享**：同一个簇内的核心访问同一份数据不需要经过内存
- **降低延迟**：簇内核心访问 L2 缓存比访问内存快得多
- **提高效率**：减少内存带宽占用

### K1 的两个簇

K1 有 2 个簇，共 8 个核心：
- **簇 0**（Cluster 0）：4 个 X60 核心 + 4 个 A60 核心，共享 L2 缓存
- **簇 1**（Cluster 1）：4 个 X60 核心（无 AI 扩展），共享 L2 缓存

### K3 的两个簇

K3 有 2 个簇，共 16 个核心：
- **簇 0**（Cluster 0）：4 个 X100 核心 + 4 个 A100 核心，共享 4MB L2 缓存
- **簇 1**（Cluster 1）：4 个 X100 核心 + 4 个 A100 核心，共享 4MB L2 缓存

### 簇与缓存层次

**类比：图书馆取书系统**

```
L1 缓存（你的桌子）
  - 最快：0.5 纳秒
  - 最小：每人只有 128KB（64KB 工具书 + 64KB 笔记本）
  - 私有：每个核心独享
         ↓ 没有？去找组内书架
         
L2 缓存（组内书架）
  - 较快：5 纳秒
  - 中等：一个组共享 4MB
  - 共享：4-8 个核心一起用（这就是"簇"）
         ↓ 没有？去图书馆
         
内存（整个图书馆）
  - 最慢：100 纳秒
  - 最大：所有人共享 32GB
  - 全局：所有核心都要从这里拿书
```

**工作流程**：
1. CPU 先查桌子（L1） → 有就直接用 ✅
2. 桌子没有 → 查组内书架（L2） → 有就拿回桌子 ✅
3. 书架也没有 → 去图书馆（内存）拿 → 放到书架 → 拿到桌子

**为什么需要簇**：同一个组（簇）的人可以互相借书（共享 L2 缓存），不用每次都跑图书馆（内存），大大提高效率。

**相关概念**：缓存层次、L1 缓存、L2 缓存、NUMA

## 编码压缩比

**编码压缩比**（Compression Ratio）是指原始视频数据大小与编码后视频数据大小的比值。

### 为什么需要压缩？

**原始 4K 30fps YUV420 视频一分钟有多大？**

```
计算步骤：
1. 一帧图像大小 = 3840 × 2160 × 1.5 字节 = 12.4 MB
   （YUV420 每个像素平均 1.5 字节：Y 占 1 字节，U 和 V 各占 0.25 字节）

2. 30fps × 60 秒 = 1800 帧

3. 一分钟视频 = 12.4 MB × 1800 = 22.3 GB
```

**22.3 GB 的原始视频根本无法存储和传输！**

### H.265 编码后能压缩到多大？

**H.265 编码后**：
- 一分钟 4K 30fps 视频 ≈ 600 MB（取决于码率设置）
- 压缩比 ≈ 22.3 GB / 600 MB ≈ **37:1**

**类比理解**：
```
原始视频 = 一本厚厚的相册（每页都是完整照片）
H.265 编码 = 只保存第一张完整照片 + 后续照片的"变化部分"

例如：
- 第 1 帧：完整保存
- 第 2-30 帧：只保存"嘴巴动了""眼睛眨了"这些变化
- 第 31 帧：再次完整保存（关键帧）
- 第 32-60 帧：继续只保存变化

这样就能大幅减少数据量
```

### K3 的 VPU 支持哪些编码格式？

- **H.264 / AVC**：压缩比约 20:1，兼容性最好
- **H.265 / HEVC**：压缩比约 37:1，比 H.264 节省一半空间
- **VP9**：谷歌开发的开源格式，压缩比接近 H.265

**相关概念**：码率、关键帧、帧间预测、GOP

## AFBC

**AFBC**（Arm Frame Buffer Compression，Arm 帧缓冲压缩）是一种**硬件加速的图像压缩格式**，专门用于减少内存带宽占用。

### AFBC 的作用

**场景**：显示控制器需要从内存读取帧缓冲数据，然后发送到屏幕。

**问题**：
- 4K@60fps 显示 → 每秒读取 60 帧 × 12.4 MB = **744 MB/s**
- 如果同时有 2 个屏幕 → **1488 MB/s**
- 这会占用大量内存带宽，影响 CPU 和 AI 核心的性能

**AFBC 的解决方案**：
```
传统方式：
内存（未压缩 12.4 MB）→ 显示控制器 → 屏幕
          ↑ 占用 744 MB/s 带宽

AFBC 方式：
内存（压缩后 6-8 MB）→ 显示控制器（硬件解压）→ 屏幕
          ↑ 只占用 372-496 MB/s 带宽（节省约 40%）
```

### AFBC 的特点

1. **硬件加速**：压缩和解压都由硬件完成，CPU 不需要参与
2. **无损压缩**：图像质量不受影响
3. **实时处理**：延迟极低，适合实时显示
4. **节省带宽**：减少 30-50% 的内存带宽占用

### 类比理解

```
传统方式 = 每次搬家都把所有家具完整搬走
AFBC 方式 = 把家具拆开（压缩），到新家再组装（解压）

好处：
- 搬运更快（占用带宽更少）
- 卡车可以装更多东西（内存带宽可以用于其他任务）
- 家具质量不变（无损压缩）
```

### K3 的 AFBC 支持

K3 的显示子系统支持 AFBC 格式的帧缓冲：
- **输入**：GPU 或 VPU 输出 AFBC 格式的帧缓冲到内存
- **处理**：显示控制器直接读取 AFBC 格式的帧缓冲
- **输出**：硬件解压后发送到 MIPI-DSI 或 DP/eDP 屏幕

**相关概念**：帧缓冲、内存带宽、显示控制器、DPU

---

## CoM

**核心模组**（Computer-on-Module，CoM）是一种产品形态：把芯片、内存、存储封装在一块小板上出售。

- 卖的是**模组**，不是整机
- 客户买回去插到自己的载板（carrier board）上，仍需自己设计接口和外形
- K3 的 CoM260 属于这一形态

**与整机形态的区别**：Pico-ITX 是完整可用的单板计算机，买回去直接装进设备；CoM 必须配上客户自己的载板才能用。

**相关概念**：SoC、Pico-ITX、产品形态

---

## TOPS

**TOPS**（Tera Operations Per Second，每秒万亿次运算）是衡量 AI 算力的单位。

- 1 TOPS = 每秒 1 万亿次运算
- **必须带精度条件才有意义**：INT8、INT4、是否启用 sparse（稀疏计算）
- K1 标 2 TOPS（@INT8）；K3 标 60 TOPS（@INT4 sparse）

**为什么两个 TOPS 不能直接相除**：位宽和稀疏策略不同，"一次运算"不是同一件事。INT4 每个数只用 4 位，同样硬件一周期能塞进两倍的数；sparse 会跳过权重中的零值，进一步抬高理论峰值。要比较，需换算到同一精度，或直接比实测吞吐。

**相关概念**：INT8、INT4、稀疏计算、算力

---

## SRAM

**SRAM**（Static Random-Access Memory，静态随机存取存储器）是芯片内部的快速可读写内存。

- K3 有 **512 KB**，由主 CPU 与实时核（RCPU）共享
- **上电后立即可用**，不需要初始化 —— 这是它相对 LPDDR5 的关键优势
- 掉电数据丢失，不是存储设备
- 容量小，只够启动早期临时使用

**为什么它不可替代**：LPDDR5 上电后要初始化才能用，而这段初始化代码本身必须先有地方跑，那就是 SRAM。

**相关概念**：Boot ROM、LPDDR5、启动流程

---

## Boot ROM

**Boot ROM**（启动只读存储器）是芯片出厂时固化好的只读存储，CPU 上电后执行的第一段代码来自这里。

- K3 为 **128 KB**，不可修改
- 负责决定从哪个存储介质启动，并加载下一阶段引导程序
- 支持的来源：eMMC、UFS、SD、QSPI NOR Flash、USB、UART 下载

**为什么只有 128 KB**：里面只放最小引导代码，够把下一阶段拉起来即可。这条容量限制直接决定了启动必须分阶段进行。

**相关概念**：SRAM、FSBL、多阶段启动

---

## FSBL

**FSBL**（First Stage Boot Loader，一级引导程序）是 Boot ROM 之后运行的第一个引导阶段。

- 存放在 eMMC、SD、QSPI 等外部介质
- 主要任务：**初始化内存（LPDDR5）**，并加载后续软件
- 运行位置：此时 LPDDR5 尚未就绪，所以它先运行在片内 SRAM 里

**与 U-Boot 的分工**：FSBL 负责"把内存弄好"，U-Boot 负责"把内核装进去"。

**相关概念**：Boot ROM、U-Boot、OpenSBI、SRAM

---

## OpenSBI

**OpenSBI**（Open Supervisor Binary Interface）是 RISC-V 架构特有的固件层，运行在引导程序与 U-Boot 之间。

- 在操作系统与底层硬件之间提供**标准接口（SBI）**
- 作用：Linux 内核不必针对每颗芯片写底层代码，通过 SBI 请求定时器、处理器间通信等服务
- 类比：内核与硬件之间的"翻译官"

**技术写作提示**：文档里会看到这个名词，知道它是"内核和硬件之间的中间层"就够用，不需要展开寄存器细节。

**相关概念**：SBI、U-Boot、RISC-V、FSBL

---

## U-Boot

**U-Boot**（Universal Bootloader，通用启动程序）是最常见的嵌入式引导程序。

- 负责把 Linux 内核和设备树从存储介质加载到内存，然后把控制权交给内核
- K3 中它在内存就绪之后运行，不再受 SRAM 容量限制
- 提供命令行，供开发调试使用

**与 FSBL 的区别**：FSBL 是芯片厂商提供的一级引导，负责初始化内存；U-Boot 是通用的第二阶段引导，负责加载内核。

**相关概念**：FSBL、设备树、启动流程

---

## 设备树

**设备树**（Device Tree）是一个描述文件，记录板子上有哪些硬件、各自连接在哪里。固件中常见的文件名后缀是 **DTB**（Device Tree Blob）。

- 内核启动时读取它，据此初始化驱动
- **解决的问题**：同一颗芯片装在不同板子上，接口配置各不相同。有了设备树，内核代码保持通用，换一份设备树就能支持新板子
- 类比：房屋平面图 —— 同一套建筑结构，配不同平面图就能适配不同布局

**相关概念**：U-Boot、Linux 内核、板级设计

---

## eMMC

**eMMC**（embedded Multi-Media Card，嵌入式多媒体卡）是最常见的嵌入式主存储。

- 符合 eMMC 5.1 规范，8 位数据宽度
- 最高速度：**HS400 模式 400 MB/s**
- 直接焊在板上，不可热插拔
- 用途：放操作系统、应用和用户数据

**与 UFS 的关键区别**：eMMC 用并行总线，读写不能同时进行（非全双工），因此吞吐量低于 UFS。

**相关概念**：UFS、SD 卡、Quad-SPI、内存与存储

---

## UFS

**UFS**（Universal Flash Storage，通用闪存存储）是比 eMMC 更快的主存储接口。

- 符合 JEDEC UFS 2.2 规范，最多 2 TX + 2 RX 通道
- **串行差分、全双工**：读写可以同时进行，这是吞吐量更高的根本原因
- 支持直接从 UFS 启动
- 成本高于 eMMC

**相关概念**：eMMC、JEDEC、启动模式

---

## Quad-SPI

**Quad-SPI**（Quad Serial Peripheral Interface，四线 SPI）是低速串行 Flash 接口，专门用来存放启动代码。

- 时钟 13.25–102 MHz，数据线可配置为 1/2/4 线
- 支持 SPI NOR Flash 与 SPI NAND Flash
- 容量小（几 MB 到几十 MB），价格便宜
- 支持 **XIP**（Execute-In-Place，就地执行）：CPU 直接在 Flash 上执行代码，不必先复制到内存

**为什么需要它**：Boot ROM 之后要加载的引导程序需要一个便宜、简单、上电即可读的存放处。

**相关概念**：XIP、Boot ROM、eMMC

---

## eFuse

**eFuse**（electronic fuse，电子熔断丝）是芯片内部的一次性可编程存储，**只能写入一次**。

- K3 用它存放"哪把密钥可信"的信息（根公钥的哈希值）
- 启动时 Boot ROM 拿它来验证固件签名
- **写入后不可逆**：设备从此只认签名固件，无法回退

**为什么必须谨慎**：如果签名流程有问题或密钥丢失，设备将无法启动且无法修复。所以量产前必须充分测试签名流程。

**相关概念**：安全启动、根密钥、Boot ROM

---

## 安全启动

**安全启动**（Secure Boot）是在每次启动时验证固件来源的机制，确保设备只运行经过授权的固件。

- 核心思路：**每个阶段验证下一个阶段**（Boot ROM → FSBL → U-Boot → 内核）
- 任何一级验证失败，启动立即停止
- 依赖 eFuse 中存放的密钥信息，**本地完成，不需要联网**
- 与普通启动的区别：普通启动会运行介质上任何合法格式的固件

**相关概念**：eFuse、根密钥、信任链

---

## Fastboot

**Fastboot** 是 Android 生态广泛使用的设备刷写协议，K3 用它把固件从 PC 写入设备存储。

- 通过 USB 连接，速度快、兼容性好
- 进入刷写模式的方式：按键组合（FEL + RESET）、`adb reboot bootloader`、串口长按 `s`
- **与"卡启动"的区别**：刷写是往设备存储里**写**；卡启动是**从** SD 卡运行系统

**相关概念**：固件刷写、卡量产、下载模式
