# 安全启动与固件保护

> **本讲目标**：知道安全启动是什么、为什么需要它，以及 eFuse 是什么、为什么不能随便使用。
>
> **📌 说明**：本模块以 **K3** 为例，但安全启动的核心概念适用于所有支持此功能的 SoC 芯片。

## 一、为什么需要安全启动

正常情况下，设备会运行存储介质里任何合法格式的固件。这带来一个风险：**如果有人替换了固件，设备就会运行未经授权的代码**。

**安全启动**（Secure Boot）的作用是在每次启动时验证固件的来源，确保只有经过授权的固件才能运行。

## 二、逐级验证：每一步都检查

安全启动的核心思路是**每个启动阶段都验证下一个阶段**：

```
Boot ROM（出厂固化，无法篡改）
  ↓ 验证
引导程序（FSBL）
  ↓ 验证
U-Boot
  ↓ 验证
Linux 内核
```

**只要有一级验证失败，启动就会停止**，防止后续的恶意代码运行。

## 三、eFuse：不能反悔的开关

**eFuse**（电子熔断丝）是芯片内部的一种特殊存储，只能写入一次，无法修改或清除。

K3 使用 eFuse 存储"哪把密钥是可信的"——启动时 Boot ROM 拿 eFuse 里的信息来验证固件签名。

**最重要的一点**：eFuse 一旦写入，设备就进入了"只认签名固件"的模式，**无法回退**。

> ⚠️ 量产前必须充分测试签名流程。如果密钥丢失或签名流程有问题，设备将无法启动且无法修复。

**类比**：eFuse 像是给门锁换了一个只认特定钥匙的锁芯。换好之后就没有万能钥匙了。

## 四、两类密钥的分工

安全启动涉及两类密钥，分工不同：

| 密钥类型 | 用途 | 保管方式 |
|---|---|---|
| **根密钥** | 建立最初的信任，哈希值写入 eFuse | 极少使用，离线保存 |
| **发版密钥** | 日常签名固件发布版本 | 相对常规，可以更换 |

根密钥一旦泄露，影响无法挽回（必须重新制作芯片或批量更换 eFuse）。发版密钥泄露后换一把重新签名即可。这就是两者保管方式差别很大的原因。

## 五、OpenSBI 是什么

在 K3 的文档里你会看到 **OpenSBI** 这个名词。它是 RISC-V 架构特有的一个固件层，作用是：

**在操作系统和底层硬件之间提供一个标准接口**。

Linux 内核不直接操作 K3 的具体硬件寄存器，而是通过 OpenSBI 提供的标准接口来请求底层服务（比如定时器、处理器间通信）。这样同一个 Linux 内核可以运行在不同的 RISC-V 芯片上，不需要为每颗芯片单独修改内核代码。

**对技术写作人员的意义**：你会在启动流程文档和安全启动文档中看到 OpenSBI 这个名词，知道它是"内核和硬件之间的中间层"就足够了。
